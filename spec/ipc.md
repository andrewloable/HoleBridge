# App engine IPC

The messages the Flutter app (Dart) and the app engine exchange. The engine is `app/engine/`, run in a
Bare worklet that flutter_pear_bare starts with `BareWorklet.start(bundlePath:)`. The design is in
[app engine IPC](../docs/architecture.md#app-engine-ipc). The golden frames are `vectors/ipc.json`,
generated by `gen/ipc.js`.

**Status: proposed.** The ten open points of the first draft are decided at the end of this file
(orchestrator, 2026-10-08); the owner may revise them. Where the architecture's command sketch differs
from this spec, this spec governs.

## Transport

- One frame per flutter_pear_bare message. The frame starts at its type. flutter_pear_bare puts a
  4-byte big-endian length before each frame in the byte stream; this was read in flutter_pear_bare 0.4.9.
- On desktop the frames travel on the worklet's stdout, so the engine sends `console.*` to stderr
  (`app/engine/index.js`). A frame that does not decode exactly is `HB-IPC-DESYNC`: Dart treats it as
  fatal and restarts the worklet.
- No payload bytes cross this IPC while the data path stays in the worklet ([decisions](../docs/decisions.md) D5, proposed). If D5's fallback applies, this spec changes.
- Keys, application keys, handoff links and their secrets cross only inside frames. They never go on
  a command line or in the environment, and no log line carries them ([security](../docs/security.md), rules 1 and 5).

## Encoding

Every value uses compact-encoding 3.5.2. A frame is three fields, in order:

| Field | Type | Meaning |
|---|---|---|
| `type` | uint | the message number in the tables below |
| `id` | uint | pairs a request with its reply. Dart picks request ids, never 0. Events have id 0. |
| `body` | the message's fields | in the order listed, with no length prefix, up to the end of the frame |

Field types: `string` (length-prefixed UTF-8), `uint`, `bool`, `fixed32` (32 raw bytes, used for the
application key), `array of T` (count, then the items), and `struct` (its fields in order). `route`
and `bind` are strings with the values listed. Addresses are IPv4 strings, as in the wire handshake.
Empty values mean none: `""` for a string, `[]` for an array, `0` for a port.

## Reply

Every request gets one reply, type 0, with the request's id. Only the connect reply fills `route`,
`services` and `ports`; every other reply sends them empty.

| Field | Type | Meaning |
|---|---|---|
| `ok` | bool | the request succeeded |
| `code` | string | an `HB-` code from [errors.json](errors.json); empty when `ok` |
| `detail` | string | text for a person; see the rules for strings below |
| `route` | string | connect, when `ok`: `lan`, `direct` or `relay`, the route the session came up on |
| `services` | array of string | connect, when `ok`: the service names the host shares, from its handshake |
| `ports` | array of struct of `service` (string) and `port` (uint) | connect, when `ok`: the local port bound for each service |

## Requests (Dart to engine)

| Type | Name | Body |
|---|---|---|
| 1 | `connect` | `host` string; `key` string; `appKey` fixed32; `lan` struct of `addresses` (array of string) and `port` (uint); `ports` array of struct of `service` (string) and `port` (uint); `bind` string |
| 2 | `close` | `host` string |
| 3 | `status` | `host` string |
| 4 | `relay` | `key` string; `appKey` fixed32 |
| 5 | `handoff.listen` | none |
| 6 | `handoff.cancel` | none |
| 7 | `handoff.send` | `link` string; `name` string; `key` string; `appKey` fixed32 |
| 8 | `vpn.start` | `services` array of struct of `host`, `service` and `address` (strings) and `port` (uint); `dnsUpstream` array of string |
| 9 | `vpn.stop` | none |

- `connect` registers the host under `host`, with its key, application key, requested local ports and
  bind address, and binds the listeners. It opens the host's session if none is up, so the reply can
  carry the route, services and ports (point 2). The reply comes when the route is chosen, or when the
  search gives up after 60 s: then `ok` is false with `HB-LOOKUP-TIMEOUT`, and the host stays registered
  and retries on its own until `close`. `bind` is `127.0.0.1`, or `0.0.0.0` for **Share with my network**
  ([cli](../docs/cli.md)). An empty `lan` means no LAN address is known.
- `connect` for a `host` that is already connected replies `ok` false with `HB-USAGE` and changes nothing.
  A rename is a `close`, then a `connect` under the new name.
- `close` ends the host's session and listeners and unregisters the host. It replies `ok` even for a host
  that is not connected.
- `status`, and any other request naming a host that is not connected, replies `ok` false with `HB-USAGE`.
- `relay`: the relay key. An empty `key` means no relay, and `appKey` is then ignored (send 32 zero bytes).
- `handoff.send`: `link` is the TV's link from `handoff.code`. `name`, `key` and `appKey` are the host the user picked.
- `vpn.start`: see point 7 for `port` and `dnsUpstream`. `address` is the service's VPN address, in the
  range 198.18.0.0/16 ([architecture](../docs/architecture.md#vpn-mode-android-and-ios)).

## Events (engine to Dart)

| Type | Name | Body | Sent |
|---|---|---|---|
| 100 | `route` | `host` string; `route` string: `lan`, `direct`, `relay`, `looking` or `unreachable` | on each route change |
| 101 | `session` | `host` string; `up` bool | when a session comes up or goes down |
| 102 | `status` | `host` string; `route` string (as above, or `""` when no session is up and no search runs); `sessions` uint; `streams` uint; `flows` uint; `bytesIn` uint; `bytesOut` uint; `nat` struct of `host` (string, public IPv4 address, empty when unknown), `port` (uint), `firewalled` and `randomized` (bool) | after a status request |
| 103 | `vpn` | `port` uint; `addresses` array of struct of `host`, `service`, `address` and `name` (strings; `name` is `<service>.<host>.internal`) | after `vpn.start` |
| 104 | `services` | `host` string; `list` array of string (service names); `ports` array of struct of `service` (string) and `port` (uint) | when a handshake completes, and when a services message arrives (M3) |
| 105 | `reject` | `host` string; `service` string; `code` string (an `HB-` code); `reason` string | when the host rejects a stream |
| 106 | `error` | `code` string (an `HB-` code); `detail` string | when an error with a code happens |
| 107 | `handoff.code` | `link` string | after `handoff.listen` |
| 108 | `handoff.received` | `name` string; `key` string; `appKey` fixed32 | when the TV accepts a box |
| 109 | `lan` | `host` string; `addresses` array of string; `port` uint | when a handshake carries the host's LAN addresses (its `lan` flag) |

- `status`: `sessions` is 0 or 1, since one session per app and host is the rule ([decisions](../docs/decisions.md) D4).
  `streams` and `flows` count the open TCP streams and UDP flows on the session. `bytesIn` and `bytesOut`
  count the payload bytes received from and sent to the host since the session came up, 0 when none is up.
  `nat` is the engine's own NAT view, the same for every host.
- `services`: `ports` gives the local port bound for each service in `list` now. A service with no port bound
  has no entry.

## Type numbers

The table is append-only. Requests are 1 to 99, events 100 and up, and the reply is 0. Once a number
is committed it is never renamed, renumbered or reused. A new request takes the next free number from
10, and a new event the next from 110. `gen/ipc.js` checks the ranges and that no number repeats.

## Rules for strings

`reason` and `detail` are shown to people. They carry no key, application key, handoff secret,
token or payload byte, and no address or service name (point 9).

## Decided points

The first draft left these open. Each is decided here with the rule the orchestrator applied: follow
the docs where they say anything, and where they are silent, take the minimal option both sides can implement.

1. **Reply type.** The reply is type 0 and reuses the request's id. Type 0 stays append-only with the rest.
   Decided (orchestrator, 2026-10-08); the owner may revise.

2. **Connect reply.** The architecture's connect sketch says the reply carries the route, the services and
   the local ports bound, so the reply has those three fields (see Reply). That needs the route at reply time,
   so `connect` opens the host's session when none is up. This reads a connect as a use of the host.
   D17 and the sessions section open a session when a service is used, so this conflicts with them. The
   idle rule still applies: a session that no stream ever uses closes 5 minutes after its connect.
   Decided (orchestrator, 2026-10-08); the owner may revise. If the owner keeps this reading, D17 needs a new entry.

3. **What `host` is.** The name the app saves for the host, the same name VPN names use. The engine treats it
   as an opaque string, unique among the connected hosts. Renaming is a `close`, then a `connect` under the
   new name. Decided (orchestrator, 2026-10-08); the owner may revise.

4. **`ports` in connect.** Each entry is the local port the app saved for that service, or the one the user
   set by hand ([cli](../docs/cli.md), local ports). A port of 0, or a service with no entry, means none saved:
   the engine then binds the host's port hint from the handshake, and if that port is taken or not allowed, the
   OS picks a free one. The reply and the `services` event report the ports bound, and the app saves them. The
   hint never crosses the IPC. A saved port for a service the host no longer shares is not bound.
   Decided (orchestrator, 2026-10-08); the owner may revise.

5. **Which application key.** Dart holds the application keys in secure storage and chooses; the engine holds
   no list. Each `connect` carries one. For a host typed as 9 symbols, Dart connects with each held key in turn,
   and on `HB-LOOKUP-TIMEOUT` it closes the host and tries the next. The key that connects is saved with the host.
   Each failed try can take up to 60 s. Decided (orchestrator, 2026-10-08); the owner may revise.

6. **Relay and the application key.** [security](../docs/security.md#relay-keys) derives the relay's two key pairs
   from the relay key and the deployment's application key. The relay is set once for the app, not per host, so the
   engine cannot take the application key from an earlier connect. `relay` therefore carries `appKey`.
   Decided (orchestrator, 2026-10-08); the owner may revise.

7. **VPN ports and DNS.** In `vpn.start`, `port` is the engine's local listener for that service, the port the
   network stack hands the service's streams and flows to (the port from `ports` or the `services` event).
   Dart assigns each service's `address` from 198.18.0.0/16 and sends it. `dnsUpstream` is the device's DNS
   servers, which Dart reads from the platform and sends, because the engine cannot read them; an empty list means
   the engine forwards nothing and answers only the service names. In the `vpn` event, `port` is the local UDP port
   on 127.0.0.1 where the engine answers DNS for those names and forwards other queries. The engine picks it (an
   OS-chosen port), and the network stack sends DNS packets there. Each `addresses` entry echoes the address Dart
   sent, with `name` `<service>.<host>.internal`. The host label is the host name lowercased, each run of characters
   other than a to z and 0 to 9 replaced by one dash, with dashes trimmed at the ends
   ([architecture](../docs/architecture.md#vpn-mode-android-and-ios)). Decided (orchestrator, 2026-10-08); the owner may revise.

8. **Reject codes.** Wire reject codes map to catalog codes: 1 `HB-UNKNOWN-SERVICE`, 2 `HB-LIMIT-REACHED`,
   3 `HB-TARGET-REFUSED`, 4 `HB-TARGET-TIMEOUT` (all in errors.json). Any other wire code is malformed input
   ([architecture](../docs/architecture.md#malformed-input)): the stream ends and no `reject` event is sent.
   Decided (orchestrator, 2026-10-08); the owner may revise.

9. **Addresses in strings.** `reason` and `detail` carry no address and no service name, because
   [security](../docs/security.md#rules-for-implementers) rule 1 redacts them from error messages. The architecture's
   example reject text, "ssh refused: connection refused at 127.0.0.1:22", is therefore not carried. The app words
   the message from the code and the structured `service` field, which is data, not message text. The architecture
   example conflicts with that rule, so the architecture text is what the owner may revise.
   Decided (orchestrator, 2026-10-08); the owner may revise.

10. **Status and event triggers.** The `status` event is described under Events, and gains `sessions` so it stands
    alone. `services` is sent when a handshake completes and on each M3 services message. `lan` is sent when a
    handshake carries LAN addresses. Decided (orchestrator, 2026-10-08); the owner may revise.

## Vectors

`vectors/ipc.json` has a `vectors` list with one entry per example: `name` (the message name and its example
number), `type`, `id`, `value` (the body fields as JSON; `fixed32` as 64 lowercase hex digits) and `hex` (the whole
frame). The values are test values only: placeholder keys, an application key of bytes 0x00 to 0x1f, and addresses
from the documentation ranges. `cd spec/gen && node ipc.js` writes the file, and a second run gives the same bytes.
