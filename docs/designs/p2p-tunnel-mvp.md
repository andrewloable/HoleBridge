# Design: HoleBridge MVP, a peer-to-peer tunnel that just works

Generated by /office-hours on 2026-10-08
Branch: main
Repo: andrewloable/HoleBridge
Status: APPROVED
Mode: Builder

**What HoleBridge is.** A peer-to-peer tunnel, like holesail.io. A host shares named services, and
an app holding the key connects straight to that host. It is **not a mesh or VPN**: devices never
join a network, never get addresses on one, and never see each other. Where this doc says "instead
of a VPN", it describes how the owner uses HoleBridge, not what it is. (Framing corrected
2026-10-08; the review records further down keep their original wording.) Later, decisions D37
made the app on phones and TVs work like a VPN app, with VPN mode replacing Keep running on Android
and coming to iOS in M5. It is still a tunnel to one host's named services.

## Problem Statement

A home-lab owner wants to use their own self-hosted services (Jellyfin, web apps, SSH, a NAS) every
day from every device they own: Android phone, iPhone, Android TV, laptop. At home and away, with no
port forwarding and nothing to babysit.

Today the choices are:

- **Port forwarding with dynamic DNS.** Puts the services on the public internet.
- **A hosted reverse tunnel.** A third party relays every byte, and needs an account.
- **A mesh VPN.** Joins whole devices into a network, which is more than reaching a few services,
  and is always on.
- **Holesail, the closest fit: a peer-to-peer tunnel.** But it has one port per process and long hex
  `hs://` keys. Its official iOS app (Holesail Go) has an embedded browser, but the clients are built
  around ports, not services.

HoleBridge is the holesail kind of tool: a peer-to-peer tunnel, done for many services at once.

## What Makes This Cool

You reach your home services from anywhere, with no port forwarding. You open the app, tap a
service, and it works: over the LAN at home, direct or through your own relay when away, and it
keeps working when the phone switches networks. Nine characters, no account.

It is a tunnel to services, not a network. A session exists while a service is in use and closes
when idle, so there is no always-on connection draining the battery or getting killed in the
background.

## Constraints

- **Stack:** a Go host and relay. A Flutter app for Android phones, Android TV and Google TV,
  iPhone, macOS, Windows and Linux. A JavaScript engine in a Bare worklet on the app.
- **No usable Go HyperDHT exists,** so HoleBridge builds one: the host and relay run on pears-go,
  a pure-Go Pear library in this repo (`pears/`, no cgo). The app runs HoleBridge's own JS engine
  (`app/engine/`) through flutter_pear_bare, and flutter_pear is never modified (decisions D31, D32,
  D34, added after the reviews below; the review text assumes the earlier plan).
- **iOS suspends the networking of backgrounded apps.** For other apps to use the tunnel in the
  background, iOS needs a Network Extension.
- **Platform floors:** flutter_pear_bare needs Android 10+, and Flutter has no official tvOS support.
- **Licensing:** Holesail is AGPL-3.0 and HoleBridge is MIT, so HoleBridge is built clean-room.
- **Docs:** project docs never name the owner's other projects.

## Premises (all agreed)

1. **A tunnel to services, not a network.** The job is reaching your own services daily on every
   device. HoleBridge connects an app to one host's named services (tiles, an in-app browser,
   127.0.0.1 ports for other apps). It is never "join my network": no mesh, and devices never see
   each other. Full-subnet access stays a VPN's job.
2. **Just works = the MVP.** All three routes (LAN, direct, relay) and surviving a network switch
   belong in the first usable release, ahead of access control. (UDP joined the MVP later,
   decisions D33.)
3. **On demand, and iOS proven early.** Connect when a service is opened and close after idle.
   Prove an iOS Network Extension in the M1 spike, because the iPhone is a daily device.
4. **The in-app browser is the default.** Web services open in it by default, and it fixes what
   breaks in other tunnel browsers:
   - logins are kept separate per service;
   - self-signed HTTPS is accepted once per service;
   - links that point at the server's own address are routed through the tunnel.

## Approaches Considered

- **A. Reliable MVP, roadmap re-ordered.** Chosen; see below.
- **B. On-demand engine + browser proxy.** Deferred. It gives the best browser (a real origin per
  service) and iOS parity through a Network Extension. But Bare inside an extension's memory limit
  is unproven, and it is the longest wait for daily use. M1 data decides whether to revisit it.
- **C. Per-service virtual addresses.** Turned down for this design; adopted later for phones and
  TVs with a C network stack (decisions D37). The OS VPN interface would cover only
  HoleBridge's address range, with a Go network stack turning packets into streams. That would start
  turning a tunnel into a network. It also takes the device's single VPN slot and needs a Go stack
  plus Bare in one process.

## Recommended Approach

**Approach A.** Keep the architecture in `docs/architecture.md` and change what the first usable
release contains:

1. **The MVP covers every route and every switch.** It includes the relay route (and
   `holebridge relay`) and stream resume across network and route changes, not just LAN and
   direct.

   **Resume semantics:** these are the ones `docs/architecture.md` ("Sessions and reconnects")
   already specifies, moved from M4 into the MVP.
   - **Byte-exact, for every TCP stream.** It works below the application layer, so HTTP
     playback, SSH and uploads are treated the same.
   - **Local sockets stall, never close.** While the tunnel is rebuilt, the 127.0.0.1 sockets
     stay open for a 60 s grace period, and both sides keep unacknowledged bytes: up to 4 MiB per
     stream and 32 MiB in total.
   - **Limits close streams.** A stream whose new session does not form within the grace period,
     or that exceeds the caps, closes as it would without resume.
   - **M1 adds a resume spike.** Target: a Wi-Fi to mobile-data switch stalls streams for at most
     5 s at p50 and 15 s at p95 when a direct or relay route re-forms.
2. **On-demand sessions.** A tap on a service, or a connection to its local port, opens the session
   if none exists. The session closes 5 minutes after its last stream closes. Quiet but open
   streams, such as an idle SSH session or paused playback, keep it alive while they exist;
   keepalives hold the NAT mapping but are not streams. The app keeps the last route and
   LAN address so the next connect is fast.

   Who owns the 127.0.0.1 listeners when the app is not on screen:

   | Platform | Listeners and wake-on-connect |
   |---|---|
   | Desktop | The app process (tray, start at login) always holds them; a connection on a local port opens the session. |
   | Android (phone, TV) | With **Keep running** on, a persistent foreground service holds the listeners even when no session exists. It does no network traffic while idle: the P2P session is torn down, only the listeners remain. It uses the `specialUse` foreground-service type with a Play declaration. With Keep running off, the listeners exist only while the app is open. |
   | iPhone | Only while the app is in the foreground, until a Network Extension exists. No wake-on-connect. |

   The value claim is therefore "no always-on *network traffic*". It is not "no background
   process": Android's Keep running is a resident process with a notification, and the user
   chooses it.
3. **In-app browser requirements:**
   - storage (cookies, local storage) kept separate per service;
   - trust on first use for self-signed HTTPS, per service;
   - navigation to a service's original address mapped onto the tunnel.

   **Minimal disclosure for the third point.** By default the host sends no target or origin, and
   the browser maps only the host's own LAN addresses, which the LAN route already sends.

   A host owner may add an optional `origins` list to a **web** service in `host.json`, e.g.
   `["https://jellyfin.example"]`, naming exactly the scheme, host and port the service uses in
   its own absolute links. Only those listed origins are sent, only for web services, and only to
   key holders. Nothing is ever derived automatically from the target, so a NAS behind the host
   reveals nothing unless its owner opts in.

   This narrows the "target address is never sent" rule. The change is recorded in
   `docs/decisions.md` as part of Next Steps.

   **Per-platform browser and fallback.** The M1 spike gives each platform a pass or fail: does a
   usable WebView exist, and can it keep storage separate per service? (Candidate APIs: Android
   multi-profile WebView, iOS 17+ and macOS 14+ data stores by identifier, WebView2 profiles on
   Windows.)

   | Spike result | Open does |
   |---|---|
   | Pass | Opens the in-app browser. |
   | WebView present, no isolation | Opens the in-app browser with one shared store. The app warns that logins can collide between services. |
   | No usable WebView (expected on Linux desktop, possible on some Android TVs) | Opens the system browser at the 127.0.0.1 address, or shows the address on a TV with no browser. |

   In every case the user taps **Open** and never types a port.
4. **Service kinds: the host decides, the app never probes.** A service's kind is `https`, `http`,
   `tcp`, `udp` or `unknown`, and it travels in the service list. The kind includes the scheme, so
   Open knows which URL to load.
   - **Detection.** When a service is added, and at host start, the host checks its own target
     locally: first a TLS handshake plus one HTTP request (self-signed certificates accepted for
     the check), then plain HTTP. An HTTP response over TLS means `https`; over plain TCP, `http`.
   - **Only a reachable target can be classified.** A target that accepts the connection but
     answers neither way is marked `tcp`. A target that cannot be reached at all (refused, timed
     out, name not resolved) is *not* classified. It keeps its previous kind, or `unknown` if it
     never had one. The host retries the check when the next stream to it opens, and then once a
     minute until it classifies, so a NAS that boots after the host is picked up.
   - **An explicit `--kind https|http|tcp|udp`** on `holebridge service add` is stored in
     `host.json` and never re-probed. A service of kind `tcp` is never sent HTTP, and `udp` is
     always explicit (decisions D33).
   - **Tiles render before a session opens.** The app caches the service list per host from the
     last session. The first-ever list arrives with the first session.
   - **What the app shows:** `https` and `http` get **Open**, which loads the matching scheme; `tcp`
     and `udp` get **Copy address**; `unknown` gets **Copy address** and **Try opening**, which
     loads `https`, then `http`.
5. **Background:** see the listener table in item 2. iOS is foreground-only, with the in-app
   browser, until a Network Extension is proven.
6. **The M1 spike gains four items, each with a pass rule:**

   | Spike | Pass rule | If it fails |
   |---|---|---|
   | iOS Network Extension | The engine runs inside the extension and holds a session plus 10 streams under the extension's memory limit, with at least 20% headroom | Reconsider Approach B or C for the iPhone |
   | Lazy connect | A cold connect from mobile data to a home host takes under 10 s at p50 and 20 s at p95, with at least a 95% success rate | Keep sessions warm longer by default |
   | WebView isolation | Per platform, as in item 3 | That platform uses the fallback in item 3 |
   | Resume | As in item 1 | Resume moves out of the MVP; the MVP closes streams on a drop |

7. **The key decision is taken in M1, before the derivation freezes (decisions Q2).** Key length is
   part of the frozen derivation and its test vector (the extra secret became the deployment's
   application key, decisions D35), so the owner decides Q2 at M1 exit, before the freeze, as
   `docs/roadmap.md` already orders it. Before the M2 build starts, the owner also decides whether
   scoped keys move into the MVP as the minimum access-control floor. The M2 release gate only
   checks that both decisions are recorded in `docs/decisions.md`.

   The accepted risk, if 45 bits stays and scoped keys stay in M4:
   - every key holder reaches every service;
   - guessing costs are as in `docs/security.md`;
   - the mitigations are rotation (`key --rotate`, in the MVP), services keeping their own login,
     and README guidance never to expose an unauthenticated admin service.

## Open Questions

- Is 5 minutes the right idle timeout? Lazy-connect measurements may move it.
- Will Play accept the `specialUse` foreground-service declaration for Keep running? (Since D37:
  will Play accept HoleBridge's `VpnService` declaration, decisions Q9.)
- Still open from `docs/decisions.md`: Q1 (the slowest device). Q2 (the 45-bit key) is settled by
  D38 (2026-10-08; Recommended Approach item 7, decisions D28). Q13 (how a TV store app gets the application
  key) is settled by D36: a handoff from a phone over the LAN.

## Success Criteria

Success is judged per platform.

- **Android phone, Android TV and laptop:** for two weeks, you reach your home services only
  through HoleBridge.
- **iPhone, MVP without a Network Extension:** every web service you use works in the in-app
  browser while the app is open. Native iPhone apps in the background still need whatever you use
  today, and that is the expected MVP state, not a failure.
- **iPhone, once a Network Extension passes its M1 rule and ships:** the two-week criterion applies
  to the iPhone too.
- **Whether the extension joins the MVP.** It does if *both* hold:
  - the extension spike passes;
  - the Assignment list shows at least one native iPhone app you use daily for a home service.

  Otherwise it follows the MVP.
- Cold connect from mobile data to a home host takes under 10 s at p50; a LAN connect takes under
  2 s.
- Playback survives a switch between Wi-Fi and mobile data with no visible interruption.
- With both ends on mobile data, the connection works through your own relay.
- Nobody types a port number to open a web service in the app.

### R3-1 — completeness (blocking)

**Problem**

> Persisting from R2-2. The new text keeps refused, timed-out and unresolved targets out of classification, but three parts of the original obligation are still unmet. (1) No probe timeout or phases are given, so 'timed out' (unclassified) and 'accepts the connection but answers neither way' (tcp) cannot be told apart: a slow-to-answer web service, or one held silent until a socket-activated service starts, is marked tcp. R2-2 asked for the timeout explicitly. (2) A target that accepts and then resets or closes while its backend starts (typical of a published-port proxy or reverse proxy just after a reboot, when the host and the service start together) counts as reachable and is marked tcp, replacing a previous https or http kind. An auto-detected tcp is then re-checked only at the next host start, a tcp service is never sent HTTP, and it offers only Copy address, so the user cannot Open a web service until the owner restarts the host or overrides with --kind. That is the same flip-on-restart failure R2-2 described. (3) 'Keeps its previous kind' needs the detected kind to survive a host restart, but only an explicit --kind is said to be stored in host.json; if a detected kind lives in memory, every host start begins at unknown and the rule that protects a previous kind never applies at the moment the check runs.

**Remedy**

> State the connect timeout and the response timeout. Say that a connect failure or timeout is unreachable (unclassified), and that a connection that is accepted and then closed, reset or left silent is inconclusive, not tcp. Classify tcp only when the target stays open and either sends non-HTTP bytes or gives the same result on repeated probes. Never replace a previous http or https kind with tcp on a single probe. Re-check an auto-detected kind on a timer or on the next stream, not only at host start. Say where a detected kind is persisted so a restart keeps it.

Question D7:
D7 — Should each process cap the total memory its stream windows can hold?
Project/branch/task: HoleBridge on main, eng review Performance, plan docs/designs/p2p-tunnel-mvp.md.

Header: Receive budget
Options:
A) Budget per process (Recommended)
